# Safe publication using the connected Atlassian tools

These instructions reconstruct authored records, not account permissions. Never infer that a project with a matching key is a test project. Confirm its AsterBridge name and the explicit authorized site first. Leave all unrelated projects and content untouched.

1. Discover accessible resources, visible/create-capable Jira projects, issue types, required/optional fields, priorities, transitions, and link types. Save the actual responses. Project creation and Confluence space creation were not exposed by this plugin; the original three Jira projects and ABL space were created through authorized browser setup. Use supported UI or an authorized project API if absent. Do not substitute an existing production project.
2. Use JQL `labels = "asterbridge-labs-v1"` with complete pagination to discover existing seeded issues. For each local seed, match the unique `abl-seed-<seed_id>` label, verify the exact project, and retain the returned issue ID, key, and URL. Stop on duplicate seed markers instead of choosing arbitrarily.
3. Create epics first, then standard work items, then subtasks. Payloads come from `jira/seed-issues.json`. Map `parent_seed` to a confirmed native key. Use metadata-approved priority, due date, and labels. Never create an assignee account or use a fictional employee name as an account ID. Set a native assignee only after verifying an actual disposable test account.
4. Apply observed supported transitions. This site's transitions were To Do 11, In Progress 21, and Done 31; rediscover them in another environment. Business Blocked maps to In Progress plus `abl-blocked` only where a native Blocked transition is absent. Preserve the distinction in descriptions and tests.
5. Once all issue keys exist, resolve every dependency text to actual source URLs. For each relationship, inspect the saved current `issuelinks` first. Create only a missing exact type and endpoint pair. Under this connector's contract, `inwardIssue` is the blocker and `outwardIssue` the blocked issue. Verify the resulting source issue has the expected outward target.
6. Before adding history, read all issue comments and look for `ABL-HISTORY:<seed_id>:v1`. The original seed created one native comment per issue containing two dated narrative entries. Skip a matching marker. If the content needs correction, update that exact comment ID rather than adding duplicates. Dates in the narrative do not backdate Jira's real comment timestamp.
7. Save every mutation response immediately. Reconcile after any timeout before retrying; an uncertain response does not mean creation failed. Read back every final issue with `*all` fields and complete comments. Store complete snapshots in `jira/snapshots/`. Preserve actual creation and update timestamps and source-qualified identities.
8. Discover the authorized Confluence space and list/search all pages with complete pagination. Match exact prefixed titles and verify the parent tree. Create only missing pages. The original environment uses one ABL space with Company, Engineering, ATLAS, BEACON, and HARBOR logical groups. Use the prepared Markdown bodies and actual Jira links from `confluence/pages.json`.
9. Create the group overview pages before their children. Save returned page IDs, original URLs, versions, and actual space ID in `confluence/remote-map.json`; save response bodies separately. Use a version-safe update only when an existing dataset-owned body actually differs. Do not overwrite customer pages.
10. Rebuild the business files and evaluation cases after publication maps are complete. Refresh the source manifest and validate. Keep unpublished OneDrive item IDs and URLs null. Microsoft upload and ACL setup require an explicitly authorized folder and appropriate account access; do not infer confirmation from the local folder name.

No credentials are part of the export. Authentication remains with the connected tools. For reruns, use both remote marker discovery and local maps; neither a stale local map nor a matching display name alone is enough.
